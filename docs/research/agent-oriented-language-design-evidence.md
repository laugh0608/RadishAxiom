# 面向 Agent 的语言设计：证据与开放问题

用途：记录与 RadishAxiom 定位直接相关的外部证据、证据边界和可检验假设，为后续目标领域、Axiom IR、语义与评测设计提供输入。

读者：项目维护者、语言与验证研究者，以及准备设计基准任务的协作者。

不包含：正式语法、实现语言、验证后端、产品路线或已经接受的架构决策。本文是非规范性研究备忘；正式口径仍以产品定义、ADR 和专题规范为准。

更新日期：2026-08-18

状态：Research note

## 当前结论

1. 已有证据支持一个有限结论：在边界清楚的任务中，显式、受约束、规范形式较少的领域表示可能降低 Agent 的生成错误。
2. 现有证据不足以证明通用编程语言将消失，也不足以证明任意新 DSL 都比成熟语言可靠。
3. “机器规范表示 + 人类投影 + 确定性编译 / 验证”已经存在现实案例，但不能据此提前冻结 RadishAxiom 的表面语法。
4. 训练语料少、领域规则缺失和语义幻觉仍是新 DSL 的重要风险；新语言不能只依靠模型自行猜测。
5. RadishAxiom 应先把这些判断转化为可复现实验，再把实验结果升级为语法、IR 或工具链决策。

## 外部证据评估

### Anka：受约束 DSL 的窄域实验

[Anka 预印本](https://arxiv.org/abs/2512.23214)设计了一门面向数据转换管道的 DSL，强调单一规范形式、命名中间结果、显式步骤和冗长关键字。论文在 100 个任务上报告：Claude 3.5 Haiku 对 Anka 的解析成功率为 99.9%，总体任务准确率为 95.8%；在多步任务中，Anka 为 100%，Python 为 60%。GPT-4o-mini 的交叉模型实验也报告了优势。

它支持的判断：

- 模型可以通过上下文示例学习未见过的窄域语言；
- 限制等价写法、显式命名状态和固定操作顺序可能减少多步生成错误；
- 训练语料数量不是生成可靠性的唯一决定因素。

它不能直接支持的判断：

- 结果只覆盖数据转换、100 个任务和有限模型，不能外推到通用软件工程；
- 解析成功不等于语义正确，更不等于形式证明；
- 论文没有证明 S-表达式、依赖类型或某个验证后端是最佳选择；
- 预印本结果应通过独立复现、更多模型和隐藏测试继续核验。

### Flint：语义中间语言与多后端编译

[Flint 项目](https://microsoft.github.io/flint-chart/)和[对应预印本](https://arxiv.org/abs/2607.20775)展示了一种语义驱动的可视化中间语言：Agent 或用户提供紧凑的图表类型、字段映射与语义类型，编译器确定性补全布局和后端细节，再生成 Vega-Lite、ECharts、Chart.js、Plotly 或 Excel 输出。

它支持的判断：

- 小型语义契约可以把 Agent 从大量低层参数中隔离出来；
- 同一规范表示可以服务多个后端，而后端差异留在编译层；
- 人类可编辑输入、机器规范化和生成结果可以是不同表示层。

它不能直接支持的判断：

- Flint 证明的是一个具体中间语言架构可工作，不是对通用 Agent 编程语言的验证；
- 自动补全默认值依赖领域规则，本身可能成为需要审计的信任边界；
- 多后端输出不自动保证不同后端具有完全相同的行为语义。

### 新 DSL 的上下文与训练风险

[Microsoft 的 DSL 实践文章](https://devblogs.microsoft.com/all-things-azure/ai-coding-agents-domain-specific-languages/)指出，新 DSL 因训练暴露少、语法分歧和领域上下文不足，容易导致模型猜测、虚构 API 或混淆相似语言；文章同时建议用精选示例、显式规则、检索上下文和验证反馈改善生成。

该文章引用的“初始低于 20%、干预后最高约 85%”是实践性综合数字，不应成为 RadishAxiom 的验收阈值。对本项目更重要的结论是：语言规范、示例、错误协议和验证反馈属于产品能力，而不是发布后再补的文档工作。

### 语言熟悉度不是唯一变量

[MirrorCode 论文](https://epoch.ai/files/MirrorCode_8ae911f.pdf)让 Agent 使用 Python、C、Rust、Go、OCaml 和 Ada 重建既有命令行程序，并报告不同语言上的总体表现相近。这个结果可以反驳“训练数据少的语言必然不可用”的绝对判断，但它测试的是成熟语言上的程序重建，不是新 DSL 学习，也不涉及形式验证。

因此，RadishAxiom 不应假设模型天然会使用新语言；也不应仅凭训练语料少就否定新表示。两种判断都需要本项目自己的基准数据。

## 这些材料没有证明什么

- 没有证明 Python、TypeScript 或其他成熟语言会被新语言取代。
- 没有证明每个垂直领域都值得创建独立 DSL。
- 没有证明“约束越多，正确性越高”；错误、遗漏或过弱的规范仍可被实现完全满足。
- 没有证明机器友好与人类可读必须按固定字符比例分配。
- 没有证明 S-表达式优于其他规范化树表示、结构化 schema 或受限文本语法。
- 没有证明 SMT、证明助手、符号执行或动态检查中的任一种可以独立覆盖目标问题。
- 没有证明大型业务系统可以依靠自动生成的契约和证明报告获得端到端正确性。
- 没有证明编译器产生的自述报告等同于可由独立小检查器复核的 Evidence。

## 与当前项目口径的对应

现有正式文档已经吸收并修正了早期材料中的主要方向：

| 早期问题 | 当前项目口径 |
| --- | --- |
| “约束即正确性” | 正确性只相对于明确规范成立；规范本身也必须接受审查 |
| 机器与人类可读性的比例 | Axiom IR 是规范化语义，人类通过稳定投影、语义差异和反例审阅 |
| 编译器即审计员 | 输出必须区分 `proved`、`checked`、`unknown`、`failed` 和 `trusted` |
| 自动生成证明报告 | Axiom Evidence 必须版本化、可导出并支持独立检查 |
| 先选 S-表达式或实现语言 | 先选择目标领域，定义语义、IR、验证义务与 Evidence，再冻结表面语法和技术栈 |
| 从通用语言开始扩张 | 首版选择边界清楚的窄领域，打通可复验闭环后再判断泛化价值 |

正式边界见[产品定义](../product-definition.md)和[当前状态](../status/current.md)。

## RadishAxiom 的待验证假设

以下内容是研究假设，不是项目承诺：

- **H1：规范形式假设。** 每个操作只有少量或唯一规范形式，比提供大量等价语法更能降低 Agent 的解析和操作排序错误。
- **H2：显式状态假设。** 命名中间结果、显式效果、信任边界和验证状态，可以降低隐式状态造成的语义错误。
- **H3：双投影假设。** 同一 Axiom IR 可以同时提供稳定机器序列化和无损的人类审阅投影，而不形成两个语义真相源。
- **H4：反馈闭环假设。** 结构化验证义务、最小反例和机器可读错误，比自由文本报错更能帮助 Agent 稳定修正程序。
- **H5：独立证据假设。** 独立小检查器对 Axiom Evidence 的复核，可以显著缩小对生产编译器、求解器适配层和报告生成器的信任。
- **H6：窄域迁移假设。** 在一个边界清楚的领域验证有效的语义构造，可以在保持证据边界的前提下迁移到相邻领域。

## 最小实验要求

冻结表面语法或主要验证后端前，至少设计一组能够反驳上述假设的基准：

1. 选择具有明确输入、输出、错误条件和隐藏边界案例的窄领域。
2. 对同一任务建立至少三种表示：该领域常用语言、普通结构化 schema / DSL、候选 Axiom 规范表示。
3. 使用多个模型和固定上下文预算，分别测试零样例、少样例和带验证反馈的生成。
4. 区分解析成功、类型 / 效果通过、契约满足、真实任务语义正确和 Evidence 可复核，不能合成一个成功布尔值。
5. 覆盖正例、负例、欠约束规范、错误规范、恶意输入、求解器 `unknown` 和显式 `trusted` 边界。
6. 对规范形式、命名中间状态、语法外壳、人类投影和错误协议做消融实验，避免把多个变量的收益归给单一语法选择。
7. 记录修正轮数、token / 时间成本、验证时间、反例质量、隐藏测试通过率和跨模型稳定性。
8. 在查看完整结果前定义成功阈值和停止条件；失败结论同样进入研究记录。

## 对当前开发顺序的影响

- 不因这些材料创建编译器骨架、S-表达式解析器、Z3 接线或完整工具链。
- 先选择首个目标领域与基准任务，再定义能表达该领域的最小类型、效果、契约和失败语义。
- Axiom IR 的候选设计必须能支持版本化、规范化、差异比较和至少一种人类投影。
- Axiom Evidence 的候选设计必须先定义状态语义、信任清单、反例和独立检查边界。
- 技术栈比较必须以基准需要、可信计算基和可复现实验为依据，而不是沿用早期 AI 对话的实现建议。
