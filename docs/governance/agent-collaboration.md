# RadishAxiom Agent 协作与执行规则

用途：承接 `AGENTS.md` / `CLAUDE.md` 不适合在每次任务启动时全量加载的稳定协作细则。

目标读者：维护者、贡献者和自动化协作者。

不包含：当前阶段、近期优先级、临时门禁、专题技术契约、命令级验证流水或历史记录；这些内容分别归入[当前状态](../status/current.md)、对应专题、ADR 或记录。

## 文档职责

| 层级 | 职责 | 典型内容 |
| --- | --- | --- |
| 根入口 | 必须启动即生效的长期契约 | 授权边界、协作原则、可信性红线、任务路由 |
| 稳定专题 | 按任务读取的长期详细规则 | 产品、语义、格式、实现、验证、仓库治理、协作流程 |
| 当前状态 | 随阶段变化的现行口径 | 当前顺位、临时门禁、“当前不做”、验证入口 |
| 记录与归档 | 已发生的事实和证据 | 实验结果、验证流水、批次交接、历史推演 |

根入口不是项目手册的副本，`docs/README.md` 也不是阶段规则正文。入口负责说明“去哪里读”，专题负责解释“规则是什么”，当前状态负责说明“现在做什么”，记录只保存可追溯事实。

发生疑似冲突时，先按文件职责判断：法律授权与安全披露优先，产品定义和已接受 ADR 决定长期边界，专题规范决定对应领域契约，当前状态决定未被长期决策覆盖的阶段口径，根入口决定协作者如何执行任务，自动化只实施已声明规则。不能用较低层实现静默改写较高层语义。

## 任务推进

### 开始任务

1. 读取 `git status`，确认分支、ahead / behind、暂存区、未暂存和未跟踪内容。
2. 将工作树内容区分为本任务改动、用户已有改动和可能的并行改动；无法安全合并时停止写入并说明冲突。
3. 判断任务属于回答、诊断、设计、实现、治理、验证还是发布，不从一种请求推导范围外写入或外部操作。
4. 识别是否影响正式语义、信任边界、公共格式、兼容性、许可证、依赖、用户数据或远程设置。
5. 只沿根入口任务路由读取必要真相源；需要历史证据时再读取记录或归档。
6. 查找现有实现、测试、脚本和命名惯例，确认是否已有稳定入口可以扩展。

询问“下一步做什么”时只先读 `docs/status/current.md`。状态信息不足以判断长期边界时，再进入产品定义、ADR 或相关专题；不要默认展开全部历史、实验记录或兄弟项目。

### 分析与批准

- 用户只要求分析、解释、审查或建议时，不擅自修改仓库或远程状态。
- 用户明确要求修改且范围清楚、风险可控时，直接实施并完成风险匹配的验证。
- 不同合理解释会改变语义、用户行为、数据模型、兼容性、信任、许可证或外部影响时，先说明关键判断；只有缺失选择会实质改变结果时才停下询问。
- 已授权方案若出现实质性范围变化，应暂停扩张并重新确认，不能把变化隐藏在实现细节中。
- 修改长期规则时同步检查文档、自动化和远程配置模板，但远程写入仍需独立授权。

### 实施与收口

- 优先解决根因、边界和同类缺陷，不只修复一个表象后留下明显重复问题。
- 不做玩具式最小实现、占位逻辑或无法覆盖主要路径的半成品。
- 不做与目标无关的重构；直接影响需求的结构问题可进行必要且边界清楚的修正。
- 抽象必须服务于真实复用、边界隔离、复杂度下降或领域契约；简单逻辑不通过多层包装制造间接性。
- 错误处理只覆盖明确的输入、IO、网络、权限、资源、并发和兼容风险，不吞异常、不伪造成功、不用默认值掩盖契约问题。
- 完成可分割步骤后执行相应最小验证；命令成功后仍须检查预期产物、状态变化、诊断和负向结果。

出现多种可行方案时，依次判断需求和声明是否完整准确，语义、信任和证据边界是否清晰，架构与兼容性是否可维护，修改范围与实现复杂度是否受控，验证是否与风险匹配。不能用“范围更小”越过正确性和信任问题，也不能用抽象完整性扩大无关范围。

## 工作区与临时产物

- 用户已有、未跟踪或并行写入的内容默认属于用户；不覆盖、不回滚、不移动、不顺手暂存或提交。
- 修改与现有差异重叠时先理解完整 diff，再做最小兼容编辑；不以重写整文件规避冲突判断。
- 破坏性操作前解析并复核精确目标；不得对仓库根、用户目录、未解析变量或宽泛 glob 执行递归删除、覆盖或批量移动。
- 临时脚本、日志、截图、Evidence 和调试产物放入任务专用且已忽略的位置；只清理本任务创建且确认无保留价值的内容。
- 不为通过格式门禁批量改写第三方、上游镜像、生成文件或明确需要保留原格式的资料。
- 任务结束前复核 `git diff`、`git status` 和未跟踪文件，确认没有秘密、缓存、意外换行、权限变化或越界文件。

## 授权、进程与环境

### 依赖和外部状态

- 安装、升级或移除依赖前，说明命令、用途、目标版本、依赖声明与 lockfile 影响、维护和许可证风险，并取得当前任务授权。
- push、PR、tag、Release、部署、远程配置、Secrets、外部消息和系统设置是彼此独立的授权动作；commit 授权不包含其中任何一项。
- 用户授权只覆盖已经说明的命令与范围；目标、版本、依赖面或运行影响发生实质变化时重新确认。
- 不跨工作区修改兄弟项目，不把兄弟项目文件整套复制进本仓库；引用时提炼原则与接口，并使用稳定在线地址而非一次性本机路径。
- 不用管理员 bypass 取代正常 PR 流程，也不把仓库中的声明式模板误认为远程设置已经生效。

### 服务与后台进程

- 启动长期运行服务、桌面程序、浏览器或临时代理前，说明命令、端口、预计运行方式、主要影响和清理方式，并取得当前任务授权。
- AI 启动的后台进程在任务结束前按约定关闭并报告；用户自行启动的进程不擅自停止。
- 不沿用历史会话中的启动、登录或授权状态；真实运行态验证前重新确认当前任务所需环境。

### 沙盒与敏感信息

- 构建、测试和最小验证默认先在当前环境执行。
- 因权限、PATH、网络、证书或平台限制无法取得真实结果时，保留原始错误并判断环境特征；必要时申请以最小范围在更真实环境复验同一命令。
- 提权不扩大任务授权，也不能成为修改产品代码以适应异常环境的理由。
- 凭据、token、私钥、恢复码和真实敏感输入不得进入命令参数、日志、截图、fixture、Evidence、提交或对话摘录。

## 依赖、第三方材料与生成产物

- 标准库或现有依赖能够清晰解决问题时，不为便利新增依赖。
- 新增依赖时记录用途、精确版本策略、维护状态、许可证、供应链风险和可替代方案。
- 依赖声明和 lockfile 通过对应包管理器维护，不手工伪造解析结果；意外 lockfile 漂移必须查明原因。
- 第三方代码、数据、模型、字体、示例或资产必须记录来源、版本、许可证和必要归属；公开可访问不代表可自由再分发。
- 生成代码、绑定、schema、fixture 或 Evidence 必须能追溯生成入口和输入；需要提交时明确源文件、再生成方式和人工修改边界。
- 测试、文档和示例使用合成或脱敏数据，不复制真实用户内容、专有输入、安全报告或生产凭据。

## 文件与代码

- 仓库自有文本使用 UTF-8 无 BOM、LF、末尾换行且无尾随空格；换行、缩进和二进制类型遵循 `.editorconfig` 与 `.gitattributes`。
- 本地状态、缓存、生成物和凭据遵循 `.gitignore`，不得为方便而提交环境文件。
- 命名必须表达语义或领域职责，不使用含义不清的缩写和技术包装名。
- 优先显式类型、结构化数据、标准能力和顺序控制流；不依赖动态字符串状态、全局隐式状态、影响阅读的函数套函数、深层回调或只转发参数的 wrapper。
- 注释解释原因、约束和不明显的权衡，不复述代码；行为变化时同步更新或删除失效注释。
- 新增公共格式必须包含版本或明确演进策略，并提供正例、负例和兼容性测试。
- 单个源码文件接近 1000 行时评估按领域或稳定边界拆分，原则上不继续超过 1500 行；生成文件和有来源的上游材料除外。
- 目录优先浅层职责分组；稳定入口留在目录根，内部实现、fixture 和 helper 进入含义清楚的子目录。
- committed 相对路径默认不超过 180 字符，单文件默认不超过 10 MiB；较长语义进入结构化元数据，不持续拉长路径和文件名。

## 文档归位与维护

- 产品定位、命名或长期边界变化时更新产品定义；当前阶段、下一决策、临时门禁或验证入口变化时更新当前状态。
- 架构、语义、公共格式或治理决策变化时新增或更新对应 ADR / 专题；许可证、贡献授权或商业边界变化时同步检查 LICENSE、许可策略、CONTRIBUTING 和 README。
- 优先更新已有正式文档，不为一次性讨论创建平行真相源。同一主题出现多个文件时，明确当前规范、事实记录和历史参考的身份。
- 入口文档保持简洁；历史推演、命令流水、实验结果和批次证据进入专题、记录或归档，正式结论回写产品、ADR、专题或当前状态。
- 新增或大改长文档时，在开头说明用途、目标读者和明确不包含的内容；不要让同一文件同时承担入口、规范、历史流水和完整参考四种职责。
- 文档篇幅按阅读成本而非机械行数治理。参考目标：Agent 根入口与其他入口 / 索引 10 KB、`docs/status/current.md` 8 KB、ADR 12 KB、Guide / Runbook 15 KB、Architecture / Boundary 25–30 KB；接近预算时优先拆成入口摘要与专题正文。
- 项目日期使用 Asia/Shanghai（UTC+8）。长期文档引用兄弟项目时使用项目名和稳定在线地址，不写入任务临时提供的本机路径。

## 验证策略

- 小型文档改动至少检查链接、术语、镜像文件与 `git diff --check`；治理改动还须运行当前仓库级检查，并复核文档、workflow、Ruleset 和检查器契约。
- 普通实现改动执行对应模块的格式化、静态分析、构建和精准测试；跨模块、公共接口或用户主路径变化再扩大到集成、端到端或运行态验证。
- 语义、IR、Evidence 或信任边界改动必须增加正例、负例、反例与兼容性验证。
- 修复健全性问题时，先加入能暴露错误结论的回归用例，再修正实现。
- 涉及独立检查时，测试必须覆盖生成器和 checker 结论不一致的拒绝路径。
- 涉及资源消耗或恶意输入时，验证终止、超时、内存和输入规模边界。
- 静态检查、mock 或 headless 结果不能替代未覆盖的真实入口、平台行为、外部工具交互或人工可见结果。
- quick / fast 模式只能用于开发反馈；阶段合并、发布或其他正式门禁以当前状态、治理专题和对应检查入口为准。
- 验证失败先保存命令、退出码和关键错误，再判断代码、数据、测试、工具或环境根因；不得因重跑成功就忽略不稳定性。
- PR 和交接只记录实际执行过的验证；未执行、失败、受环境阻塞或只能静态复核的项目必须分别说明。

## Git 与交接

- 提交使用 Conventional Commits，按可审阅主题拆分，不混入无关重构，不添加 AI 协作者署名。
- 暂存前复核完整 diff，按精确路径加入本批文件；存在无关变更时不使用会扩大范围的批量暂存。
- 未经明确要求不 amend、重写、合并或拆分既有提交，不修改用户 Git 身份，不用 reset、rebase 或 force push 处理共享历史。
- 提交后复核提交摘要和工作区状态，报告 commit hash、剩余改动以及相对远端的 ahead / behind 状态。
- 普通变更进入 `dev`；阶段性稳定化从 `dev` 向 `master` 发 PR；紧急修复使用 `hotfix/*`。合并方式、Ruleset 和回流细节以[仓库治理](repository-governance.md)与 [ADR 0001](../adr/0001-branch-and-pr-governance.md)为准。
- 最终总结先说明实际结果，再列关键行为变化、实际验证、未验证内容、剩余风险、`unknown` / `trusted` 边界、兼容性影响和待人工外部动作。
- 只有必要工作和验证已经完成时才表述为“完成”；占位实现、待授权外部动作或关键验证阻塞必须显式保留。
- 报告工作区是否干净，是否存在未提交或未推送提交、后台进程和任务专用临时产物。

## 根入口维护

一条规则只有同时满足以下条件，才进入 `AGENTS.md` / `CLAUDE.md`：

1. 跨任务成立，而不是某个功能或批次专属；
2. 跨开发阶段成立，不会随当前里程碑自然失效；
3. 必须在协作者读取专题文档前生效，否则容易产生高风险或大范围错误；
4. 无法只通过任务路由和对应专题可靠承载。

不满足这些条件的内容归入稳定专题、当前状态、记录或归档。长期但只与特定任务有关的详细规则也应放入专题，而不是因为“长期有效”就复制到根入口。

`AGENTS.md` 与 `CLAUDE.md` 必须逐字一致。修改根入口时同步检查本专题和关联真相源；修改阶段状态、临时门禁或批次事实时不反向修改根入口。根入口以短、稳定、可路由为目标，参考阅读预算为 10 KB，不以机械行数替代内容审查。
