# RadishAxiom 许可证与生态策略

状态：已采纳

日期：2026-08-18

## 当前决定

RadishAxiom 的原创代码、文档与配置采用 [Apache License 2.0](../LICENSE)。

这一决定不照搬 Radish 家族其他应用项目的 source-available 条款。RadishAxiom 是语言、IR 与验证基础设施，只有允许个人和组织自由试用、修改、分发及商业集成，才有机会形成编译器后端、编辑器、SDK、验证工具与领域适配器生态。

Apache License 2.0 同时提供明确的版权与专利授权，并保留商标边界。项目不通过自定义许可证增加解释成本，也不以限制使用领域或禁止商业使用的方式建立壁垒。

## 长期目标

许可证策略服务于以下目标：

1. 让 Axiom IR、Axiom Evidence 和验证状态成为可共同实现的开放协议，而不是单一服务的私有格式。
2. 让企业能够把编译器、验证器与 SDK 嵌入现有工具链，而不必先进行特殊授权谈判。
3. 让研究者和开发者能够复现实验、构建新后端并独立检查验证结果。
4. 让项目可以通过服务与专业能力持续发展，而不是依赖对基础工具链的使用限制。

## 开放基础层

以下能力原则上属于 Apache-2.0 开放基础层：

- 语言规范与规范化规则；
- `raxc` 编译器及其核心命令行工具；
- Axiom IR 的结构、序列化格式和兼容性规则；
- 验证状态、信任边界与 Axiom Evidence 格式；
- 能够独立检查 Evidence 的最小可信检查器；
- 参考解释器或参考验证器；
- 公共 SDK、协议定义、兼容性测试与最小示例；
- 维持生态互操作所必需的参考后端和适配器。

开放基础层必须保证：用户无需依赖专有在线服务，也能生成、检查、导出和审计核心语义与证据。商业产品可以增强效率、规模和体验，但不得成为解释 Axiom Evidence 的唯一真相源。

## 商业化边界

项目的可持续商业空间主要放在基础工具链之上，包括：

- 托管验证、求解器调度、缓存与大规模并行基础设施；
- 企业身份、权限、审计、密钥与私有部署集成；
- 面向特定行业的连接器、合规策略包与报告工作流；
- 高可信部署、长期支持、性能优化和响应保障；
- 兼容性认证、安全评估、培训与专业服务；
- 不改变公共语义和证据格式的高级协作与治理功能。

商业层与开放基础层应保持清晰的仓库、模块和依赖边界。不得为了制造付费门槛而故意削弱开放检查器、隐藏必要格式，或让公开工具只能读取而不能独立验证证据。

## 用户程序与生成产物

设计目标是：使用 RadishAxiom 编写的程序及其生成产物，不因使用编译器而被强制采用 Apache-2.0。

如果生成代码嵌入项目运行时、模板或库，应为这些组件建立明确且宽松的授权边界，避免许可证意外传递到用户程序。引入第三方运行时、求解器、字体、模型或数据集时，仍须分别记录并遵守其许可证。

## 品牌与认证

Apache License 2.0 不授予 RadishAxiom 名称、Logo 或其他品牌标识的商标权。未来可以建立独立的商标与兼容性认证规则，用于区分：

- 官方发行版；
- 兼容实现；
- 修改后的非兼容分支；
- 通过指定测试套件的认证实现。

商标与认证规则只能保护来源和兼容性表达，不应被用来限制合法的代码使用、修改或再分发。

## 外部贡献治理

- 默认遵循 `inbound = outbound`：贡献以 Apache-2.0 提交并并入 Apache-2.0 项目。
- 开始接受规模化外部贡献前，应补充贡献指南，并评估使用 DCO 记录贡献来源与授权声明。
- 如果未来确实需要对同一核心代码提供专有双重许可，必须在接受相关外部贡献前建立明确的 CLA、版权转让或其他足够的再许可授权；DCO 本身不提供专有再许可权。
- 不应在贡献者已形成后，假定可以单方面收回或改变已发布版本的 Apache-2.0 授权。

## 未来许可证调整原则

Apache-2.0 是语言与开放基础层的默认长期选择。只有出现可验证的问题时才重新评估，例如长期存在无法回流的核心私有分支，并已实质损害兼容性或维护能力。

届时可以考虑：

- 对新的、边界清楚的组件采用 MPL-2.0，以要求对已分发的受许可文件修改保持开放；
- 对独立托管服务组件单独评估网络 copyleft 或 source-available 方案；
- 在语言规范成为独立公共标准时，评估是否为规范文本采用更适合引用、翻译和标准传播的文档许可证。

任何调整都必须先确认版权归属、依赖兼容性、已有贡献授权和迁移影响。已经依据 Apache-2.0 发布的版本，其既有授权继续有效。自定义许可证、AGPL 或 BSL 不作为编译器、IR、Evidence 格式和最小检查器的默认选择。

## 复核时点

出现以下事件时，应重新复核本策略，但不预设必须更换许可证：

- 发布首个可用的编译器、SDK 或包；
- 接受第一批外部代码贡献；
- 成立承接版权或商标的法律实体；
- 推出托管服务或企业版；
- 引入会进入生成产物的运行时或模板；
- 发布稳定语言规范或兼容性认证计划。

许可证或贡献协议的重大变更在实施前应接受专业法律审查。
