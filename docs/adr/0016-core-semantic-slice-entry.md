# ADR 0016：核心语义切片的分阶段实施入口

日期：2026-09-29

状态：Accepted

用途：把核心语义组件的实施前置与完整管线、产品隔离的验收前置分开，规定 P1–P2 的有限入口和完成标准。

不包含：改变首域语义、接受新工具或依赖、运行 solver / Node / checker、创建公开 CLI、安装 / 激活 runtime、发布 Evidence v0.2 或接受来源声明。

## 背景

[开发计划](../development-plan.md)要求分别验收核心能力和产品运行能力；[首切片依赖审阅](../axiom-pipeline-first-slice-dependency-review.md)已确认 P1–P3 技术上不依赖产品 VM 或 checker 激活。[ADR 0007](0007-first-verification-first-compilation-pipeline.md#进入受控实现的验收条件)仍要求首个实现变更前同时满足八项入口，导致局部组件也等待完整工具与运行链。

本决策调整实施先后，保留规范、生产门控和独立复核要求。近期投入与顺位调整的事实见[阶段整理记录](../records/2026-09-29-core-realignment.md)，不作为本 ADR 的长期规则。

## 决策及适用范围

本决策仅窄替代 ADR 0007 中“开始任何实现都须同时满足全部入口”的要求，允许先实施生产方向的内部 Rust 语义组件。ADR 0007 的两个公共 mode、完整 P0–P9、阶段失败含义与所有下游门控继续有效；旧 ADR、语义、IR、Evidence 和机器契约的摘要绑定原文不修改。

首批从已有 Axiom IR candidate bytes 开始，先完成 P1 组件，再进入有明确义务版本的 P2。主仓沿用已接受的 Rust 2024 / `1.97.1`；在既有 workspace 内按实际领域职责落地，不为尚未实现的阶段创建空模块、通用框架或第二套公共入口。模块名称和最小依赖清单在首次实现前对照已有实现确定。

此处的“组件完成”不等于完整 P1 / P2 生产阶段、管线或产品已验收。内部函数和测试可接受固定版本 / 摘要及有界输入，不能因此声称已经实现 P0 invocation、生产 receipt、Evidence 装配或独立 checker。

### 八项入口的具体处理

编号对应 ADR 0007 原入口。下表只是组件阶段的例外；未完成项仍须在完整管线验收前补齐。

| 原入口 | 组件实施前仍须满足 | 后续补齐、不得提前宣称的内容 |
| --- | --- | --- |
| 1：profile / mode / policy | 明确组件的输入版本、摘要、范围和资源拒绝边界；引用现有契约 | 完整 invocation 与全部 adapter 的实际消费 |
| 2：制品规范字节 | P1 遵循完整 IR v0.1；P2 须先闭合下述义务版本入口 | query、target、host data、receipt 的生产生成能力 |
| 3：场景与停止线 | 本组件的正确、非法、未支持和资源失败材料及明确终点 | 四题全部下游运行矩阵；仍保留原场景 ID |
| 4：错误门控 | 非法或未完成输入不产生成功输出；没有下游工具启动能力 | 全管线 gate、cache 与 target 不执行的集成负例 |
| 5：跨平台字节 | 使用平台无关规则和独立期望；先记录已验收宿主的真实结果 | 六个平台实际一致性，未执行平台明确为未验证 |
| 6：失败与恢复 | 原输入、实现版本、实际输出 / 错误与测试材料可追溯 | receipt、attempt、缓存与管线恢复；本切片不实现这些功能 |
| 7：独立验收 | 期望不能由生产 helper 自己生成；保留人工推导与独立材料 | 对真实 Evidence digest 的外部 checker 结果；单元测试不替代它 |
| 8：工具与依赖 | 实际使用的宿主 Rust 工具、crate、许可 / build script / native code 均须已验收 | 本组件不使用的 cvc5、Node、Linux builder 和 guest 工具，不列为组件入口 |

不得把历史工具 pin 当作当前机器已安装的证明。首次实现前只核对实际会用到的宿主工具和依赖；缺少必需材料时停在该具体依赖，不自动启动 Linux 工具链取证。依赖新增、升级或 lockfile 变化仍须另行说明和授权。

### 第一切片：P1 IR 与类型检查组件

输入为精确绑定现行语义的 IR v0.1 candidate bytes。成功输出为实际计算的 canonical IR 与内容身份；失败返回可定位的内部诊断。不得生成完整 Evidence、pipeline receipt、`proved` 或 checker 接受结论。

验收必须覆盖：

- 严格 JSON / Unicode、UTF-16 属性名排序与 Unicode scalar 语义的区别、数学整数文本、闭合成员、规范排序和内容 ID；不能把当前 runtime 的 ASCII parser 当完整 IR 实现。
- 类型、效果、引用、DAG 和契约结构，拒绝未知版本 / 字段 / tag、缺失或错配身份、重复键、未配对 surrogate、越界及循环等材料。
- 同一 IR 抽象值的合法表示变化得到相同 canonical bytes；不擅自将语义等价但规范未允许归一化的程序合并。
- 四题现有候选作为回归输入，并增加不依赖题名、已知摘要、固定字段名的同域合成输入。错误算法的 candidate 若结构合法，P1 应接受其结构，不能提前伪造验证失败。
- 资源或操作失败与确定的非法 IR 分开。实现中的规模上限、拒绝条件和未覆盖范围必须显式记录，不能将实现未支持或预算耗尽标为规范非法。

允许按可审阅子步骤编写实现，但只有上述范围通过才能称 P1 组件完成。尚不支持的范围明确报告，不形成虚假的全 IR 成功入口。

### 第二切片：P2 义务生成组件

P2 的额外入口是闭合 [ADR 0009](0009-axiom-evidence-v0-drift-and-migration.md) 的 group 义务版本问题。该 ADR 对现有 checker 的受限 profile 不自动授权新生产生成器按同样方式解释全部 Evidence v0.1。

进入 P2 编码前，须形成明确且获接受的生产义务 profile 决定：若按现行路线采用 v0.2，必须完成 ADR 0009 所要求的规范、正负例与迁移演练；若提出更窄的生产 profile，则先正式审阅其兼容性，不能在代码里默选或借本 ADR 悄悄接受。本项只阻断 P2，不反向阻断不消费义务版本的 P1。

P2 从规范 IR 和已接受的义务 profile 实际生成完整义务定义、稳定 ID 和排序。验收覆盖四题与同域新材料、遗漏 / 多余 / 错配义务、group 覆盖与守恒的区分，以及输入变化对集合身份的影响。不得按 correct / wrong 标签省略义务，不以 fixture 期望驱动实现；义务已生成不代表义务成立。

独立 Go checker 不得导入生产 parser、normalizer 或义务生成器。本仓可用规范推导及独立合成期望检验组件；跨仓动态差分、导入新契约或执行 checker 仍按精确范围另行验收。

### 后续阶段

P3 需在 P2 及 query 编码边界明确后单独审阅，本 ADR 不授权其生产实现。P4 / P7 的真实 cvc5 / Node 执行仍须各自来源与隔离验收；P9 后的独立复核仍须已接受的 checker 执行路径。完整纵向闭环、四题闭环、产品 qualification 与 Agent 实验的完成标准不变。

## 停止条件、后果与回退

出现规范歧义、依赖未验收、无法给出独立期望、需要改变公共格式或必须执行外部工具才能继续时，报告具体阻断和影响，只停相应切片，不伪造默认值或扩张本例外。不会把测试成功升级为形式证明、来源认证或跨平台验收。

收益是尽早检验语义规范能否被真实实现，并用输出和拒绝路径衡量进展。代价是组件与端到端能力可能阶段性不同步，必须显式记录尚未集成的门槛；若组件无法遵循完整协议，先修正设计，不创建永久研究旁路。

回退时停止尚未验收的组件入口，保留代码、负例和失败事实；不回滚规范身份，不开放 target gate，不修改已登记 inactive runtime 的能力。

## 接受与实施的关系

2026-09-29，项目所有者在规划整理后要求“提交更改，然后按照计划继续推进吧”，接受本 ADR 所列的精确组件入口例外，并开始 P1 实施。接受不扩展为依赖变更、外部执行或公共格式迁移授权。P1 验收通过后再按 P2 的专属入口推进，不再把整个产品安装链作为 P1 的默认前置。
