# ADR 0031：本地 cvc5 构建候选的来源保证边界

日期：2026-10-27。状态：**Accepted，项目所有者于 2026-10-27 明确接受 D1–D3**。本次授权先提交本批文档，再核定阶段拆分、链接输入冻结可行性与维护成本，形成下一批有限实施计划；暂不组装、构建或运行 solver，也未授权实现、安装、探针或 push。用途：为本地 cvc5 候选定义可维护的来源声明、显式减少的保证、验收与停止条件。读者：项目所有者、构建实施者与独立复核者。不定义公共 Evidence / acceptance schema，不授予分发资格。

## 背景与范围

[开发计划](../development-plan.md)要求来源工作直接服务真实语义闭环，并允许对阻断核心验收的前置提出精确替代决策。[ADR 0030 D3](0030-solver-bootstrap-ffi-and-build-provenance.md#d3e0-公开来源不足时的下一候选)要求可追溯受控构建，明确 compiler / SDK 为受信任输入。[C2 接线设计](../query/solver-cvc5-execution-preparation.md#有限缺口审阅2026-10-27)进一步要求逐项读取 / mmap / 执行、目录查找及生成输入的稳定身份绑定；当前无满足该范围的后端。继续建设完整观察器会增加线程、FD、路径竞态、可变内容版本和内核适配的维护职责。

本决定采用**受控可访问输入集合、阶段产物来源与实际链接组成对账**作为本地构建来源接受依据，取消完整逐次读取观察的要求。这减少了观察保证，并非证明两种方案等价；剩余信任必须随新产物记录。

适用范围仅为[既定构建候选](../query/solver-cvc5-build-candidate-plan.md)：cvc5 `1.3.4` / commit `f3b21c4483d3b88dc63cb7cd3e5eb092eee5e341`，Linux AArch64 LE、glibc / GCC runtime、Production 静态 CLI，沿已选源码、SDK、patch 和功能面准备的新 bytes。仅供 ADR 0028 的本地诊断候选接受，不自动扩为其他 cvc5 版本、公开发行、产品 runtime、bootstrap / F2、Go checker、Node 或任意构建服务。源码、工具、配置或宿主改变须重新审阅对应身份和资格，不能继承上次结果。

原发布 CLI 保持 `not-accepted`；新制品另有身份。LibPoly 许可缺口及 [issue #113](https://github.com/SRI-CSL/libpoly/issues/113) 不因本决定解除。没有实际输入 / 产物时不填假摘要。

## D1：限定替代的要求与保证变化

**D1–D3 已整体接受，下表仅对上述本地新候选生效；旧入口 / 配方未经显式版本迁移继续执行原规则。接受不是实现、工具接受或执行资格。**

| 原要求的精确位置 | 已接受的限定解释 / 替代 | 保持项 |
| --- | --- | --- |
| ADR 0030 D3 的“闭合本次构建的实际输入和信任声明” | 以完整可访问文件输入集合、明确的环境 / 内核输入、阶段产物链及链接对账建立来源关联；不再解释为全部实际读取事件的认证 | 原源码 / 功能面、精确工具信任、新 payload 身份、单独 E0 决定；D1 / D2 不变 |
| 构建候选方案“消除系统选择、缓存与隐含 patch”第 5 项及“从输入到新 bytes 的留证与验收”中的逐项输入关系 | 全量 header / SDK 库存属于可访问集合；`.d`、trace 等属于有范围的使用观察。不得再声称每个 translation unit 的全部实际读取已重建 | 完整配置、生成来源、对象 / archive / link map / response file / ELF 对账；未知组成仍拒绝 |
| C2 接线设计“真实适配器的输入、输出与失败边界”之“输入读取”，以及完整读取后端门禁 | 用本 ADR D2 的隔离、阶段封闭、外部记录与 D3 验收替代；不再要求部署完整 syscall 读取观察器 | 无网络 / 宿主输入 / 共享缓存、不可变输入、资源强制、观察必要事实丢失即失败、独立终止和原授权边界 |
| C4 / E0 对新候选的来源审阅 | 接受记录必须显式标明本 ADR 与新私有规则版本、减少的保证及 trusted 构建工具 / 控制面 | 不重解释旧记录，不更改公共接受格式，不把来源核对当作形式证明或执行许可 |

接受后须同步上述专题和执行清单中适用于新候选的引用；不整体 Supersede ADR 0030，不改写已绑定旧文档、配方或历史记录的字节。尚未迁移的旧入口继续执行旧规则，不能删除一个 blocker 后沿用原接受含义。

| 类别 | 新方案可以声明什么 | 明确不能声明什么 |
| --- | --- | --- |
| 保留：来源与身份 | 在列明的信任前提下，精确输入 / 配方经受控阶段产生绑定产物，实际链接组成可对账 | 来源无缺项仅凭清单自报成立；编译器诚实性已独立证明 |
| 保留：隔离与失败 | 指定配置通过实际资格检查，未批准通道不可用；失败材料和边界均留存 | 只因 `network=none`、只读挂载或模拟通过就获得资格 |
| 减少：读取粒度 | 保存有覆盖说明的工具观察，并保守保留全部可访问材料 | 完整读取集合、全部失败查找、逐次 mmap 内容版本，或精确最小输入集合 |
| 减少：阶段内部历史 | 保留规定的阶段输出、配置、对象及链接材料 | 每个瞬时临时文件、被删除的中间版本及全部进程内部数据流已重建 |
| 原本未取得的保证 | 分别报告实际构建 / 对账结果与剩余 trust | 可复现构建、抵抗恶意 compiler / 内核、形式化构建正确性、SLSA 等级或分发合规 |

## D2：输入模型、阶段关联与信任边界

### 三类材料必须分开

1. **可访问输入集合。** 全量绑定源码 / patch、SDK / sysroot / 工具 / 头 / 库、配方和此前已冻结的阶段输出；记录路径、类型、模式、链接、长度、摘要与来源。它可以保守地包含未使用材料，不能因此把这些材料写成已读或已嵌入。未知来源、许可未接受的可访问项不能以“似乎不会使用”排除 C1 审阅。
2. **实际使用观察。** 保存工具报告的命令、配置、依赖文件、生成记录、trace、response file 等，并注明来源与覆盖范围。缺失必须保留的流 / 文件或彼此矛盾即拒绝；未要求的逐次读取信息不再作为隐含能力。工具自报内容是待核对证据，不能自己批准接受。
3. **链接组成。** 从真实有序链接命令、实际对象 / archive 成员、link map / trace、启动对象和 strip 前后 ELF 双向对账；保留库顺序与必要重复，不作集合去重。区分“归档作为输入”和“成员被抽取 / 嵌入”，未抽取项不冒充嵌入项。每项追溯到受审阅 SDK 文件或本批生成阶段；来源只有阶段粒度时明确标注，不伪造逐头文件或逐字节因果关系。

三类材料都引用同一批次、规则版本、输入根、配方与产物身份，不用一个没有覆盖说明的 `inputs_complete=true` 合并它们。整个集合闭合依赖隔离执行和受信任控制面；枚举文件后允许任意读取宿主不满足本方案。

### 阶段与链接的硬条件

[配套阶段审阅](../query/solver-local-cvc5-build-provenance-review.md#受控阶段的最小关系)要求：只读输入没有未受控可写别名；构建阶段结束并确认后代退出后才采集 / 冻结输出；下一阶段不接收未登记残留；外围记录不受构建进程控制。最终链接消费前必须冻结对象、archive、脚本和响应文件，或验收等效不可变对象方案。事后同名文件摘要不能追认消费身份。阶段拆分不改变原 flags / 顺序 / 功能面，当前配方能否提供这些边界尚未验证。

### 信任与攻击边界

| 角色 / 输入 | 剩余信任及防护责任 |
| --- | --- |
| 固定 compiler、assembler、linker、生成器及 SDK | 信任其在所列配置下正确转换并如实提供对应工具信息；保留源码 / 二进制关联和许可审阅。取消全读取观察后，对其内部数据来源的独立可见性减少；不递归重建或证明 GCC |
| 构建脚本和普通构建进程 | 可产生错误、额外访问请求或误导日志；不能掌握外围记录、隔离配置、宿主资源和接受权限。依靠已验收隔离约束可访问集合，依靠独立对账拒绝可见矛盾；不承诺识别受信任工具内部所有恶意行为 |
| 组装器、控制面、记录器及宿主 / 内核 / runtime | 信任其正确限制可访问集合、保持对象稳定、记录真实生命周期并保管输出。身份、版本、配置与资格须绑定；同一控制面采集多种证据不是多个独立信任源。不能声称防御恶意宿主管理员、内核或控制面 |
| 独立来源复核路径 | 从留存原字节及记录重算身份、检查集合 / 阶段 / 链接关系和负例；不导入生产构建器的判定函数，不依赖其 success 字段。仍信任 parser 与所列工具观察的真实性，不能独立证明没发生未记录读取 |
| solver / P4 / 独立 checker | 新工具来源接受不提高程序结论级别；sat 仍须精确重放，unsat 本地诊断不产生 proved。完整 Evidence 和独立 proof 链保持原门禁 |

选择本方案意味着明确接受这些限制，并非只接受一个较短的实现。若威胁模型要求抵抗被信任 compiler / 控制面的伪造，须另行决策，本方案不足。

## D3：验收、迁移与停止条件

### 必需验收与证据级别

[配套 A1–A10 矩阵](../query/solver-local-cvc5-build-provenance-review.md#必需验收矩阵)逐项给出正向证据、负例与拒绝：版本 / 范围、C1 输入、实际输入封闭、稳定性 / 阶段收束、生成关系、链接组成、捕获 / 信任、资源 / 终止、真实候选 / E0、旧版兼容 / 失败保留。A3 / A4 / A8 及捕获防护必须取得真实资格；离线规则或字段检查不能代替。所有项目目前均未因本决定接受而通过。

独立期望不得由同一生产 helper 生成。实际新构建及独立对账通过后，仍由项目所有者决定精确本地 E0 接受。取消完整读取日志不取消输入封闭与对象稳定；允许集合内材料缺少使用观察时，只能报告未知使用情况。观察引用集合外对象、未知生成来源或必要材料丢失仍须失败。

### 接受后的有限实施顺序

1. 先冻结本地范围、明确承担的信任和新私有规则版本，并同步被替代专题；再按具体任务授权实施。现有 `prepare-cvc5-offline-build.py` 的 v0.1、冻结配方及离线 false 标志保留；新版本必须显式选择并拒绝混配。不得给旧 JSON 手改接受字段。公共工具接受生成器若需扩展，另走 schema / 正负例 / 兼容审阅，本 ADR 不代替它。
2. 复用现有输入预检、布局、阶段配方和对象核对入口，先完成离线集合 / 阶段 / 链接验收规则及负例，再提交具体组装、阶段拆分、外部记录与资格计划。不建立通用任务调度器、完整 ptrace / eBPF / LSM 观察框架或第二套来源账本。
3. C1、真实构建环境资格及精确外部动作授权闭合后，才按 C2–C4 取得真实构建证据。依赖输出未产生前不要求假 manifest；主链接之前必须取得实际输入与冻结证据。E0 接受之后，E4 / E5 仍另行准备、验收和授权。

LibPoly、SDK / 宿主接受、扩展属性与组装差异、PID / inode、时限与整树终止这些现存缺口没有被本方案解决。原构建 4 jobs / 8 GiB / swap 0 / 20 GiB / 5,400 s 仍是待核定估算；不因监督器在树外就增加无界资源。运行继续保持原容量、旧 query / P4、十二参数、stdin 1 MiB / stdout 4 MiB / stderr 64 KiB、同 cgroup 128 MiB / swap 0 / pids 2、外层 6 s 和内部 5 s / 1,000,000 steps。

### 停止与重评

- 输入封闭、对象稳定、阶段收束、受保护记录或链接对账任一项无法实际验收，停止本候选；不改成“只有摘要也可接受”。
- 新许可 / 来源缺口、未登记通道、意外工具 / 配置 / 产物、必要观察丢失、超额或无法确认清理，首错停止并保留全部已有材料；不自动续跑、切换工具或扩大限值。
- 固定配方不能提供可冻结的链接输入，或者该方案仍需完整读取观察器 / 通用安全框架，先报告失败及成本，不把它加入默认下一任务。
- 实施前列出本批负责范围、新增可信代码职责、一次性投入和持续维护估算。现无可靠工时账；产品 runtime 的 8,000 行预警线、10 人日装置预算和每周 4 小时维护安排不能转成此方案的新额度。范围超出当前维护承受能力时提交决定，不以已投入成本为继续理由。
- 后续资格失败或重新评估撤回此范围决定时，保持新候选 `not-accepted`、`build_ready=false`；可另行选择有限 F2 静态审阅。已有布局修正、库存和失败材料保留，不反向追认原 CLI，不自动恢复另一条执行路径。

## 备选与参考

保持完整读取要求能追求更细的来源观察，但目前缺完整后端和可维护性证据；暂停并做 F2 能缩小原生缺口，却不能取得真实求解校准。选择本方案是把本地构建来源声明收窄到可验收边界，并将维护能力留给语义闭环和独立检查；不以成本理由隐藏信任减少。

设计参考 [SLSA v1.2 Build Provenance](https://slsa.dev/spec/v1.2/build-provenance)对构建平台信任与来源记录的区分。本文不直接采用其格式、依赖完备性规则或等级，也不声称符合 SLSA。长期目标与维护依据见[产品定义](../product-definition.md)、[开发计划](../development-plan.md)、[维护责任](../checker-runtime-productization-dependency-review.md#许可证与维护责任)及[阶段调整记录](../records/2026-09-29-core-realignment.md)。
