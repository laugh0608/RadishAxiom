# ADR 0003：版本标识与兼容性分层

日期：2026-08-20

状态：Accepted

用途：冻结 RadishAxiom 的项目发布标识、语义身份、公共格式版本和工具版本之间的关系，避免用一个数字同时表达发布时间、语言含义与数据兼容性。

读者：语言与验证设计者、工具链实现者、发布维护者、公共格式消费者和评测维护者。

不包含：首个具体产品版本、发布载体、表面语法、实现语言、包管理生态、tag 创建、Release、部署或发布自动化。

## 背景

[Radish](https://github.com/laugh0608/Radish) 已采用 `YY.M.RELEASE` 日历版本与 `dev` / `test` / `release` 轨道，能够直接表达一项产品在何时、以哪条轨道交付。RadishAxiom 可以复用这一家族规则，减少发布身份和仓库治理上的无谓差异。

但 RadishAxiom 不是只有一个应用版本的产品。一个工具链发布可能同时支持多个语言语义修订、Axiom IR 版本和 Axiom Evidence 版本；反过来，修复编译器实现也不应自动改变程序含义或公共格式。Cargo、npm 等生态还会把三段式数字解释为 SemVer 约束，不能因为字面形式相同，就宣称 CalVer 表达了向后兼容性。

因此，本决策复用 Radish 的项目发布标识，同时为语义、公共格式和实现保留独立身份。任何验证结论都必须引用足以重建其含义的完整版本集合，而不是只写一个产品版本或 `latest`。

## 决策

### 版本身份分层

RadishAxiom 使用四类相互独立的版本身份：

| 层级 | 回答的问题 | 身份规则 | 是否表达兼容性 |
| --- | --- | --- | --- |
| 项目发布版本 | 这是哪一次 RadishAxiom 工具链交付？ | `YY.M.RELEASE` CalVer 与发布轨道 | 否，只表达时间与发布顺序 |
| 语言语义身份 | 程序和契约按哪套规则解释？ | 当前使用规范内容摘要；未来可增加稳定语义版本到摘要的受审计映射 | 只能由语义规范与迁移规则声明 |
| 公共格式版本 | IR 或 Evidence 按哪套结构、规范化和拒绝规则解析？ | Axiom IR 与 Axiom Evidence 各自使用独立的精确版本 | 只能由对应格式规范声明 |
| 工具实现身份 | 哪个编译器、验证器、后端或检查器产生了结果？ | 工具链发布版本加组件、规则和依赖版本 | 不自动证明其实现正确或格式兼容 |

这四类身份不能互相替代。产品版本相同不代表语义或格式相同；语义摘要相同也不代表不同工具实现具有相同缺陷或可信边界。

### 项目发布版本与 tag

RadishAxiom 的项目发布版本采用：

```text
YY.M.RELEASE
```

- `YY` 是两位公历年份，例如 `26` 表示 2026 年；
- `M` 是不补零的月份 `1`–`12`；
- `RELEASE` 是当月从 `1` 开始递增的发布序号，每月重置；
- 产品版本本身不带 `v`，也不包含轨道、构建号或兼容性级别。

规范 Git tag 采用：

```text
vYY.M.RELEASE-(dev|test|release)
```

需要区分同一产品版本在同日的多个候选或修订构建时，可以采用：

```text
vYY.M.RELEASE.DDXX-(dev|test|release)
```

- `DD` 是两位日期 `01`–`31`；
- `XX` 是当日序号 `01`–`99`；
- `.DDXX` 只扩展 tag、制品与发布记录身份，不改变三段式产品版本；
- `dev` 表示内部集成候选，`test` 表示测试交付候选，`release` 表示正式发布节点；
- 轨道后缀不表示部署已经完成，也不改变语义或格式兼容性。

CalVer 只承诺可排序的发布时间和当月顺序。`26.9.1` 不因数值大于 `26.8.1` 就自动兼容后者，同一月份的两个发布也可能支持不同的格式集合；真实兼容边界必须读取支持矩阵。

### 产品版本单一真值

当前不创建产品版本文件，因为项目尚无编译器、安装包或其他需要同步的版本化产物，也没有达到首个发布候选入口。

当存在两个或以上需要共享发布身份的正式产物时，仓库根目录必须引入 `version.json` 作为唯一允许人工决定产品版本的位置。首版配置至少包含带 schema 版本的 `productVersion`；各语言清单、二进制元数据、包清单和发布记录只能由同步入口派生，并由只读门禁拒绝漂移。

版本同步不授权创建 tag、Release、镜像、包、部署或远程设置。上述动作仍分别遵循仓库治理和显式授权边界。

### 语言语义身份

当前有键有限表转换语义继续以规范文件的精确 UTF-8 SHA-256 摘要作为权威身份。Axiom IR、Axiom Evidence 与工具支持矩阵必须记录摘要；实验记录可以额外记录能够恢复该文件的精确仓库修订，但不得用 `current`、`latest`、分支名或可变 URL 替代精确身份。

未来可以为经过稳定化审查的语义快照分配便于人类沟通的稳定版本，但必须满足：

1. 一个稳定语义版本永久映射到一个精确规范摘要；
2. 制品仍保留精确摘要，稳定版本不能覆盖或替代它；
3. 值域、失败、效果、验证义务、可观察结果或信任边界发生变化时，必须形成新的语义身份；
4. 两个语义身份是否兼容，只能由明确的差异、迁移和回归证据决定，不能从产品 CalVer 推断；
5. 在稳定语义版本与兼容承诺另行冻结前，不对外宣称语义向后兼容。

规范文件的任何字节变化都会改变当前摘要；是否属于规范性语义变化还必须在评审中单独判断。文案修正不能沿用旧摘要制造内容寻址假象。

### Axiom IR 与 Axiom Evidence

Axiom IR 和 Axiom Evidence 是两个独立公共格式，各自维护版本、规范化、可接受文档集合、迁移和拒绝规则：

- 已接受的 Axiom IR 初始格式版本为 `0.1`；
- 首个被接受的 Axiom Evidence 格式使用 `0.1`，具体字段与语义由后续 Evidence 规范冻结；
- 两者不跟随产品 CalVer，不要求同时升级，也不能只因工具链发布而升级；
- 读取器必须声明精确支持的版本集合，未知版本默认拒绝；
- 版本迁移必须显式记录源版本、目标版本、迁移规则、源与目标摘要以及未保持的语义；
- 在各自 v1 兼容承诺另行冻结前，不能根据数字范围自动接受未来 v0.x。

格式版本改变的判定以对应规范为准。至少在 schema、必需字段、规范化字节、内容寻址、状态含义、拒绝边界或独立检查结论改变时，不能静默沿用原格式版本。

### 工具链与组件身份

形成可分发工具链后，`raxc` 和随同交付的默认组件共享项目发布版本，用于回答“哪次实现发布产生了这一结果”。但每份 Axiom Evidence 还必须能追溯：

- 采用的语义摘要及未来可选的稳定语义版本；
- 输入 Axiom IR 的格式版本与文档摘要；
- Axiom Evidence 的格式版本与文档摘要；
- 编译器、验证器、求解后端、迁移规则和独立检查器的精确实现版本；
- 规则集、证书格式、可信输入和未覆盖边界。

同一工具链可以支持多个明确列出的格式版本；同一格式也可以由多个工具链版本实现。支持矩阵必须列举精确集合，不能写成未经证明的 `>=`、`latest` 或“兼容所有旧版”。

### 公共包版本边界

实现语言和包生态尚未冻结，因此本 ADR 不决定未来 Cargo crate、npm package、Python package 或其他公共库的依赖版本语义。

若发布环境会把 `YY.M.RELEASE` 当作 SemVer 并据此自动放宽依赖范围，必须在首次公开包发布前单独决策：公共库是采用真正表达破坏性变化的 SemVer、使用精确版本约束，还是仅作为与工具链绑定的非独立组件。不能把 CalVer 的三段数字外形当作已经满足 SemVer 兼容承诺。

## 变更判定

| 变化 | 必须变化的身份 | 不自动变化的身份 |
| --- | --- | --- |
| 编译器或验证器缺陷修复，语义与公共格式不变 | 下一次工具链产品版本、相关组件版本 | 语义身份、IR / Evidence 格式版本 |
| 语义规范文件字节变化 | 语义摘要、引用该摘要的新制品 | 产品版本、IR / Evidence 格式版本，除非其规则也改变 |
| 可观察语义、验证义务或信任边界变化 | 新语义身份及兼容性评审 | 产品版本是否立即发布、公共格式版本是否变化 |
| IR schema、规范化或拒绝边界变化 | Axiom IR 格式版本及迁移 / 拒绝测试 | Evidence 格式版本，除非 Evidence 结构也改变 |
| Evidence schema、状态含义或独立检查边界变化 | Axiom Evidence 格式版本及迁移 / 拒绝测试 | Axiom IR 格式版本，除非 IR 结构也改变 |
| 新发布只更换轨道或同日候选构建 | tag / 制品扩展身份 | 三段式产品版本、语义与公共格式身份 |

一次变更可能同时命中多行，必须分别更新各层身份，不能为了少 bump 而把真实变化归类到较弱层级。

## 首个产品版本的分配条件

本 ADR 不给当前仓库分配 `26.8.1` 或任何其他产品版本。只有同时满足以下条件，才进入首个具体版本、`version.json` 和发布门禁设计：

1. 至少一个可重放的纵向工具链制品已经形成，不再只有设计文档；
2. 发布载体、目标平台、包含组件和许可证边界已经明确；
3. 语义、Axiom IR、Axiom Evidence 与工具组件的支持矩阵可以机器读取并接受负向验证；
4. 已定义版本同步、漂移检查、发布记录、回滚和历史制品保留规则；
5. 已完成与目标包生态的版本解析兼容性检查；
6. 具体 tag、Release 或部署动作继续获得独立授权。

满足这些条件只允许提出候选版本，不自动表示已发布、已部署或具有稳定兼容承诺。

## 后果

收益：

- Radish 家族项目共享一致、易识别的发布标识；
- 工具修复、语言含义和公共格式演进可以独立追踪；
- Evidence 能够精确说明结论基于什么语义、格式与实现；
- 未来选择包生态时不会被 CalVer 的三段数字误导为 SemVer 承诺。

代价与风险：

- 发布记录和 Evidence 必须携带多个版本身份，不能只展示一个“应用版本”；
- 维护者需要分别判断实现变化、语义变化和格式变化；
- 精确摘要会让规范文案修改产生新的内容身份，需要工具和语料库显式更新；
- 在首个真实制品出现前不会获得一个用于宣传的项目版本号，这是有意避免的虚假成熟度信号。

## 变更要求

修改产品 CalVer 格式、tag 轨道、版本单一真值、语义身份、IR / Evidence 独立版本原则、未知版本拒绝策略或首版分配条件，必须以新 ADR 替代本决策，并同步当前状态、仓库治理、公共格式规范、发布检查与兼容性测试。只分配新的具体产品版本或增加符合本决策的发布记录，不需要替代本 ADR，但必须通过届时生效的发布门禁。
